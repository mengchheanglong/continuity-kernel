## Intrinsic root cause

Installed package source order:

1. `@dbos-inc/dbos-sdk/dist/src/dbos.js:189-202`
   - creates the executor;
   - calls `await executor.init()`;
   - only later iterates registered datasources and calls `await ds.initialize()`.
2. `@dbos-inc/dbos-sdk/dist/src/dbos-executor.js:145-158`
   - initialization hooks run;
   - then `recoverPendingWorkflows()` starts inside `executor.init()`.
3. `@dbos-inc/postgres-datasource/index.ts:89-93`
   - datasource access throws `DataSource <name> is not initialized` until its hidden provider is initialized.

The durable workflow row independently recorded:

```text
status=ERROR
application_version=continuity-kernel-v0-t2-v1
executor_id=local
recovery_attempts=2
error=DataSource continuity-domain is not initialized.
```

The same unchanged pre-transaction boundary failed twice with fresh workflow IDs. Mid-transaction recovery reproduced the same error after rollback in isolation. Post-commit recovery succeeds because the completed operation can be replayed without entering the uninitialized datasource path.

No supported public API was found to initialize the exported datasource provider before executor recovery. The benchmark therefore does not apply an internal-registry workaround.
